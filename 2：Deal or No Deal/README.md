### Deal or No Deal 项目描述（AI）

#### 1. 项目目标与文档状态

使用 Python 与 LangGraph 开发一个本地运行的 Deal or No Deal 开箱谈判游戏。舞台上有 20 个装有不同虚拟奖金的箱子，选手保留其中一个，逐渐打开其他箱子；银行家根据公开局面提出收购报价，选手决定接受、拒绝或还价。银行家可以在约定的开箱间隙提前来电，打断原本连续开箱的节奏。

项目同时承担两项任务：让人能够玩完一局有悬念的游戏；通过报价分析和赛后复盘，理解期望值、风险偏好、谈判时机与停止决策。LangGraph 用于组织状态、分支、暂停和恢复，模型用于银行家的决策与角色表达，本地代码负责规则、金额计算和状态变化。

本文件是供人类检查的 AI 起草稿，只描述拟实现的功能和验收边界，不表示相关程序已经实现，也不限定具体类名或文件拆分。标题中的“AI”表示文档由 AI 起草，不表示首版必须是两个 AI 自动对局。

以下内容已来自前面的项目讨论：20 个箱子、银行家可主动介入、解释报价依据，以及最终可以当选手、当银行家或围观。未确定的细节在本稿中采用以下**待人类审核的默认约定**；审核后，实现、提示词和展示必须遵守同一份规则。

| 待审核事项 | 本稿的默认约定 |
| --- | --- |
| 首版形式 | Python 本地终端中的单局游戏，以编号菜单操作 |
| 首版参与方式 | 人类当选手，一个 AI 当银行家；主持和裁判由程序承担 |
| 金额与轮次 | 固定 20 档虚拟奖金，六轮分别开 5、4、3、3、2、1 个箱子 |
| 提前来电 | 每局最多两次，每轮最多一次；只在非轮末的开箱完成后发生 |
| 还价 | 每次有效报价最多还价一次；银行家接受该还价就立即成交 |
| 报价策略 | 模型从本稿规定的系数档位中选择，程序计算金额；这是教学策略，不是节目官方公式或最优策略 |
| 最终选择 | 最后剩两个未开箱时进行最后一次报价；拒绝后领取自己箱内的金额，不换箱 |
| 保存方式 | 本地 SQLite 检查点，支持退出后继续未完成的同一局 |

#### 2. 范围、身份与胜负含义

完整设想包含三种参与方式，但首版交付只包含第一种：

| 参与方式 | 选手 | 银行家 | 范围 |
| --- | --- | --- | --- |
| 选手模式 | 人类 | AI | 首版必须实现 |
| 银行家模式 | AI | 人类 | 后续扩展，不作为首版验收条件 |
| 观战模式 | AI | AI | 后续扩展，不作为首版验收条件 |

“用户”指运行程序的人；“选手”指持有一个箱子并决定是否成交的一方；“银行家”指提出收购报价的一方。首版中的银行家也可以在文案中被称作资本家，但两者是同一角色，不增加第三个玩家。程序主持人负责宣布事件，不需要单独调用模型。

选手尝试取得自己愿意接受的奖金结果；银行家尝试通过报价与时机选择降低本局的奖金支出。银行家支付成交价，或在始终未成交时支付选手箱内金额；它没有额外的下注资金、破产规则或独立资产账户。本项目不将一次低价成交、最终箱值或某次报价与期望值的差额直接判定为一方的绝对胜利，而是展示成交结果和分析指标。

首版不包含网页或桌面图形界面、语音、动画、联网多人、账户、排行榜、批量自动对局、模型训练、真实支付和下注。所有金额都是游戏中的虚拟奖金。自然语言自由聊天、模型直接操作文件或外部工具、自动联网查询也不在首版范围内。

首版需要能新开一局、继续一局、正常结算或明确中止。已经完成的局只允许查看记录，不允许继续开箱或修改交易。历史分支、悔棋、换箱、特别奖品及银行家临时修改规则均不在首版范围内。

#### 3. 箱子、奖金与随机性

- 箱子编号固定为 `1` 至 `20`，编号只用于选择，不表达大小、优劣或隐藏金额的线索。
- 奖金表固定为以下 20 个不同的正整数，单位为虚拟币：`1、5、10、25、50、100、200、500、1,000、2,500、5,000、7,500、10,000、20,000、30,000、50,000、75,000、100,000、250,000、1,000,000`。
- 开局时由程序将奖金均匀随机、一一分配给 20 个箱子，每一种排列等可能。分配必须发生在选手选择自己的箱子之前；之后整局不再调整，也不因模型输出、来电、还价、重试或恢复而重新洗牌。
- 选手先选择一个箱子作为自己的箱子。该箱子在游戏进行中保持关闭，不能被选作排除箱，也不能中途更换。
- 后续开箱只能选择其他尚未打开的箱子。打开表示公开金额并将该奖金排除出剩余可能金额；开出来的金额不归选手所有。
- “剩余金额”始终指所有尚未打开箱子的奖金集合，包含选手自己的箱子。奖金表、未开箱数量、已开箱记录和真实分配必须一致。
- 终局揭晓前，只有程序内部保存完整的箱号与金额对应关系。随机种子、随机生成器状态、未开箱对应关系以及可重建对应关系的调试数据均不得进入玩家界面或模型输入。
- 可以提供仅供开发验证的固定种子入口，以重现奖金分配。固定种子不保证外部模型每次产生相同的决策或台词；复现决策还需要已保存的响应或模拟响应。

#### 4. 信息可见范围

银行家与选手掌握相同的公开局面信息：完整奖金表、已开箱编号与金额、未开箱编号、选手持有的箱号、轮次、剩余开箱配额、历史报价和有效决定。银行家没有未开箱金额的特殊情报。

| 信息 | 程序内部 | 人类选手 | AI 银行家 |
| --- | --- | --- | --- |
| 开局完整箱号与金额映射 | 可见 | 不可见 | 不可见 |
| 自己保留的箱号 | 可见 | 可见 | 可见 |
| 该箱子的隐藏金额 | 可见 | 结算后公开 | 游戏中不可见 |
| 已开箱编号、金额和顺序 | 可见 | 可见 | 可见 |
| 剩余奖金集合与统计量 | 可见 | 可见 | 可见 |
| 已生效报价、拒绝和还价记录 | 可见 | 可见 | 可见 |
| API 密钥、私有存档、随机种子 | 必要时读取 | 不在游戏界面展示 | 不可见 |

模型输入必须从权威状态中按字段选取公开信息，不能把整个图状态、数据库记录、异常堆栈或内部调试对象直接序列化发送。终局揭晓前，任何提示、错误信息、复盘预告或报价理由都不能泄露隐藏金额。

银行家只能基于公开行为提出假设。例如“选手刚拒绝过一次报价”是事实，“因此可能更愿意冒险”是策略推测；不能声称已经测量出选手的真实风险偏好、接受概率、情绪或心理底价。首版不使用输入耗时、个人背景或外部个人资料作为决策依据。

#### 5. 正常开箱与报价轮次

选手选好自己的箱子后，按以下顺序推进。轮内每次只选择并打开一个箱子，不能一次提交多个编号，也不能在后台提前打开尚未选择的箱子。

| 轮次 | 本轮需打开箱子数 | 本轮结束累计打开数 | 本轮结束未开箱数，含选手箱子 |
| --- | --- | --- | --- |
| 1 | 5 | 5 | 15 |
| 2 | 4 | 9 | 11 |
| 3 | 3 | 12 | 8 |
| 4 | 3 | 15 | 5 |
| 5 | 2 | 17 | 3 |
| 6 | 1 | 18 | 2 |

每轮完成规定开箱数后，银行家必须提出一次正常报价。选手拒绝且本局尚未到最终轮时，进入下一轮；最终轮报价被拒绝时，直接揭晓选手自己的箱子并结算。

轮内提前报价被拒绝后，继续完成本轮剩余开箱数，不重置轮次、不跳到下一轮。提前报价不能替代轮末的正常报价。正常报价共最多六次，提前报价最多两次，因此整局最多出现八个初始报价机会；每次报价后的还价回应不另算一个报价机会。

#### 6. 银行家的主动介入

“打断”采用明确的游戏事件边界：一个箱子已经合法打开、金额已经公开且状态已经更新，但尚未请求选手选择下一个箱子时，银行家可以决定提前来电。它不表示异步取消一个正在运行的模型请求、在用户打字中途抢占程序，或在箱子已经确定打开后撤回开箱。

每次合法开箱后，程序按以下优先级判断：

1. 如果本轮开箱配额已经完成，进入正常报价，银行家必须报价，不消耗提前来电次数。
2. 否则，如果本局提前来电不足两次，且本轮尚未提前来电，给银行家一次判断机会。它可以选择 `wait`，或选择 `offer` 提前报价。
3. 否则直接等待选手选择下一个箱子，不为没有行动资格的银行家调用模型。

`wait` 仅表示放弃当前这一处介入机会，不消耗来电次数、不产生报价、不推进开箱。若之后仍有合资格的开箱间隙，可以再次判断。只有合法的提前 `offer` 正式生效时，才消耗一次局内及轮内额度。

报价等待答复、还价等待银行家答复、分析面板打开、选手初选自己的箱子，以及游戏结束后，均不能插入第二通来电。同一处开箱间隙最多产生一次初始报价。非法响应或 API 重试不消耗次数。

银行家的来电可以显示角色台词，例如“先等一下，我现在愿意出这个价”，但不能凭台词强迫成交、取消选择、改变奖金、追加惩罚、赠送道具或修改任何规则。首版没有报价倒计时，用户阅读分析不影响报价有效性。

#### 7. 报价金额与教学策略

银行家负责选择报价档位和说明简短依据，程序负责计算最终整数金额。首版不让模型自行计算奖金平均值或任意编造一个金额作为初始报价。

设 `R` 为当前剩余金额集合，`EV = sum(R) / len(R)`。在奖金随机分配、双方无隐藏情报的前提下，`EV` 是选手箱子最终金额的条件期望。它不是对选手本次实际所得的保证，也不等于考虑未来报价后的继续游戏价值。

六轮的基准系数如下；轮内提前来电使用当前轮的基准系数，不预支下一轮的系数。

| 轮次 | 基准系数 | 模型可选的三个系数 |
| --- | --- | --- |
| 1 | 0.45 | 0.40、0.45、0.50 |
| 2 | 0.55 | 0.50、0.55、0.60 |
| 3 | 0.65 | 0.60、0.65、0.70 |
| 4 | 0.75 | 0.70、0.75、0.80 |
| 5 | 0.85 | 0.80、0.85、0.90 |
| 6 | 0.95 | 0.90、0.95、1.00 |

模型提交 `low`、`base` 或 `high` 档位，分别映射到表中三个系数。最终初始报价统一计算为：

```text
初始报价 = max(剩余最低金额, floor(EV × 所选系数))
```

`floor` 表示向下取整到一个虚拟币；用精确的整数比例或十进制计算，避免浮点误差造成差一币。最低金额保护是报价公式的一部分，触发时必须在分析里说明。银行家不能修改系数表，也不能从无效档位静默取一个近似值。

程序将三个候选档位及其实际金额提前提供给银行家，避免让模型承担算术。不同档位可能因取整或最低金额保护得到相同金额，仍属于合法选择。新报价不保证高于上一报价；已开的奖金不同，剩余局面也会变化。

上述系数、保护规则与来电额度都是本项目的教学默认策略，不声称复现节目内部算法，不声称经过训练或求解，也不声称最优。银行家在这些边界内选择时机与档位，能观察到的是公开局面与历史行为，不能把模型猜测包装成经过校准的成交概率。

#### 8. 选手动作、报价有效期与还价

终端显示当前阶段可用的编号菜单，内部统一表示为以下动作。人类不需要手写 JSON。表中动作只有在对应阶段才合法。

| 动作 | 可用阶段 | 效果 |
| --- | --- | --- |
| `choose_box(box_id)` | 开局选择 | 将一个合法箱号确定为自己的箱子 |
| `open_box(box_id)` | 等待开箱 | 打开一个其他尚未打开的箱子，消耗本轮一次开箱配额 |
| `deal()` | 有当前有效报价时 | 接受当前报价并立即结算 |
| `no_deal()` | 有当前有效报价时 | 拒绝并使该报价失效，按轮次规则继续或最终结算 |
| `counter(amount)` | 有当前有效报价且未还价时 | 提交一次具有成交承诺的还价，等待银行家答复 |
| `explain()` | 等待开箱或等待报价决定时 | 查看当前统计量；存在报价时再展示报价分析，不改变游戏 |
| `save_exit()` | 等待人类输入时 | 保留未完成局面并退出，不结算、不判输赢 |

箱号必须是 `1` 至 `20` 的整数。还价必须是整数，严格高于当前报价，且不高于当前剩余最高金额。小数、超范围、已开箱、自选箱开箱以及当前阶段不可用的动作，都应明确报错并保持原状态。

报价在选手明确接受、拒绝或还价被银行家接受之前持续有效。不能接受旧报价、跨轮保留多个报价，或在还价尚未完成时继续开箱。程序应明确展示当前报价与其状态，不能仅凭历史记录里“最近出现的金额”认定报价有效。

每个报价机会最多有一次**合法还价**，非法输入不消耗机会。菜单在提交前说明：银行家接受还价即自动成交。银行家只有两种回应：

- `accept_counter`：按选手提出的金额立即结算，不再让任何一方撤销。
- `keep_offer`：拒绝还价，保留原报价；选手之后只能接受、拒绝、查看分析或保存退出，不能对同一报价再次还价。

银行家不能在还价答复中另报第三个金额，不能降低原报价，也不能再次提前来电。下一次新的报价机会会重新获得一次还价机会。还价可以高于 `EV`；如果银行家接受，分析必须如实显示其溢价，不能强行套回初始报价公式。

`explain()` 由本地统计和已记录的策略说明生成，不再调用模型，不推进回合，不消耗来电或还价次数。无有效报价时只显示局面统计，不编造当前报价。

#### 9. 分析面板与学习边界

分析分为“可以验证的数值”和“银行家提交的策略说明”。前者必须由程序计算，后者标明是角色选择该动作时给出的可见理由，不作为模型真实内部思维过程的证明。

局面统计至少包括：未开箱数、剩余金额列表、最低值、最高值、中位数和期望金额。偶数个金额的中位数取中间两项平均值。期望值、中位数和比例可以保留两位小数展示，但内部计算不得先使用四舍五入后的展示值。

存在有效报价 `O` 时，至少补充：

- 报价金额、正常或提前来电、当前轮次和已用来电次数。
- 初始报价的基准系数、模型所选档位、实际系数、取整过程及最低金额保护是否触发；还价成交则标明金额来自选手还价，保留原始报价作为对照。
- `O / EV` 和 `O - EV`，分别表示报价相当于期望金额的比例，以及与期望金额的差额。
- `count(x < O) / len(R)`、`count(x = O) / len(R)`、`count(x > O) / len(R)`，三项精确值合计为 100%；同时展示对应计数与总数，百分比四舍五入后的尾差不改变实际概率。
- 本次决策提交时的简短理由及相关公开事件。策略推测必须与已发生事实区分。

上述三项概率描述的是：**从当前状态开始，拒绝所有后续报价、最终领取自己箱内奖金时，该奖金与当前报价的关系**。它们不是“继续游戏会亏钱的概率”，不涵盖未来可能出现的新报价，也不能从 `O < EV` 单独推出选手现在必须拒绝。

分析不规定所有选手都应最大化期望金额。一次确定收益与一次波动很大的机会，对不同风险偏好的玩家可能有不同吸引力；首版只展示这种取舍，不虚构效用函数或为玩家自动计算一个所谓唯一正确的心理价格。

可用于验证分析的一组示例为 `R = [100, 1,000, 10,000, 100,000]`、`O = 18,000`：`EV = 27,775`，报价约为期望值的 `64.81%`；最终箱值低于、等于、高于报价的概率分别为 `75%`、`0%`、`25%`。这是独立的统计示例，不要求它必须对应首版轮次表中的某一个正常报价局面。

#### 10. 模块职责与权威状态

实现至少应分离以下职责，可以采用与斗地主项目类似的 `display`、`judge`、`bot` 与主程序结构，并增加独立的分析逻辑；此处不强制文件名称。

| 职责 | 必须承担的工作 | 不得承担的工作 |
| --- | --- | --- |
| 游戏状态与规则 | 分配奖金、验证阶段和资格、维护轮次、应用合法动作、结算 | 用模型判断动作是否合法，依据模型台词改变规则 |
| 银行家 BOT | 组织模型调用，解析行动与简短理由，报告调用结果 | 私自改状态、读取隐藏金额、执行模型返回的代码 |
| 分析 | 从公开金额与事件计算统计、候选报价和复盘指标 | 请求模型代替算术，把推测写成确定概率 |
| 显示与输入 | 展示箱子、奖金表、报价、菜单、错误与记录 | 自行判胜、维护另一套独立的奖金或轮次 |
| LangGraph 与主程序 | 调度节点、生成可见输入、提交动作、暂停恢复、保存记录 | 让界面或 Agent 绕过裁判直接执行动作 |

权威状态至少包含：规则版本、局 ID、固定奖金映射、自己的箱号、按顺序发生的开箱事件、当前轮次及剩余配额、当前阶段、提前来电使用情况、当前有效报价、还价状态、有效历史、状态版本和终局结果。

剩余金额、未开箱数和统计值必须从权威数据一致地得到；如作缓存，必须与本次状态版本绑定，不能出现页面、提示词与裁判各自使用不同局面。模型声称已成交、已开箱或已完成一轮，都不会直接使状态生效。

合法动作一次性提交后才能更新展示、消耗额度、追加有效历史并进入下一阶段。失败动作只能产生错误记录；不得部分开箱、先扣次数再回退或让同一动作结算两次。

#### 11. LangGraph 流程、中断与恢复

首版必须用 LangGraph 的显式状态与条件分支组织主流程，而不是只在外围创建一个图、内部仍由模型自由决定全部程序逻辑。

完整生命周期为：

1. 初始化本局规则和固定箱子分配，保存开局状态。
2. 暂停等待人类选择自己的箱子，校验后提交。
3. 暂停等待人类选择要打开的箱子，校验后公开金额并推进本轮配额。
4. 根据第 6 节判断正常报价、提前来电判断或直接继续开箱。
5. 有银行家行动资格时，请求模型、校验响应，再提交 `wait` 或报价；无资格时跳过模型调用。
6. 报价生效后暂停等待选手决定；还价需要额外请求一次银行家答复，异常重试除外。
7. 接受报价或还价被接受时结算；拒绝报价时，根据剩余配额继续本轮、进入下一轮或执行最终开箱结算。
8. 终局保存结果，揭晓并生成复盘，不再进入任何游戏决策节点。

人类输入使用 `interrupt()` 暂停，主程序采集操作后用 `Command(resume=...)` 恢复，并使用同一局的 `thread_id`。提前来电是第 4 步的**业务分支**，与 `interrupt()` 的**等待人类输入**职责不同，不能把两者当作同一种抢占机制。

暂停节点只负责提出当前问题和接收恢复值。模型请求、随机分配、打开箱子、扣减额度、写入有效交易等操作放在明确的独立步骤，不能放在一个恢复时会重跑的暂停节点中无保护地重复执行。

使用本地 SQLite 检查点保存完整局面。恢复必须保留原始箱子映射、轮次、报价、来电次数、还价状态和待完成阶段；不能重新初始化后仅粘贴聊天历史冒充恢复。新局使用新的局 ID，不覆盖旧局。

已提交动作需关联事件 ID 或状态版本，重复提交旧的恢复输入不得再次开箱、扣次数或成交。图重放或进程重启不能保证外部模型只被请求一次；首版要求的是已提交游戏动作不重复生效，并在调用记录中如实保留重复请求。存档规则版本不兼容或状态损坏时明确报告，不猜测修复后继续游戏。

#### 12. 模型输入、输出协议与信息隔离

模型名称、接口地址和密钥由配置提供，不在本描述中绑定某个未经验证可用的模型，不静默切换模型。首版只需支持一种明确记录的文本模型接口，并允许注入模拟响应用于验证规则；不要求多服务商适配、工具调用、流式输出或多 Agent 并行。

每次请求使用一份固定 system 规则和一份由当前权威状态构造的 user 内容。user 依次包含：

1. 本局公开规则、银行家目标、金额单位和动作协议。
2. 按事件顺序排列的完整有效公开历史，包括开箱、已生效报价、拒绝、还价及银行家的有效回应。
3. 当前阶段、轮次、配额、选手保留的箱号、未开箱号、剩余金额与精确统计，以及尚可使用的来电和还价资格。
4. 本次允许的动作；需要初始报价时提供三个候选档位和程序算出的金额，需要还价答复时提供原报价和还价金额。
5. 如果是纠错请求，提供本次最近的错误类别和原因，再次列出输出格式。

不累计旧 assistant 回复、隐藏推理内容或一整段未经筛选的聊天记录。历史中的动作与金额使用程序已验证的规范记录；无效响应、API 错误和旧台词不进入有效游戏历史。完整的原始可见文本响应单独作为调用记录保存，不回灌为下一步规则，也不包含接口的隐藏推理字段。

模型只返回一个 JSON 对象，不加 Markdown 围栏或前后文字。协议分为两种，`reason` 是必填的非空字符串，作为面向用户的简短策略说明，默认最多 200 个字符；超长或类型错误走格式纠正，不要求或展示完整内部思维过程。

```json
{"action": "offer", "level": "base", "reason": "仍有高额奖金未开，我选择当前轮的基准档位尝试成交。"}
```

- 来电判断允许 `wait` 或 `offer`；正常报价只允许 `offer`。
- `offer` 必须携带 `level`，取值仅为 `low`、`base`、`high`；`wait` 不携带 `level`。
- 此阶段不接受模型自报的 `amount`，展示金额由程序按第 7 节生成。

```json
{"action": "keep_offer", "reason": "这次还价高于我愿意支付的金额，我保留原报价。"}
```

- 还价答复只允许 `accept_counter` 或 `keep_offer`，不携带 `level` 或另一个金额。
- 对象仅允许对应协议定义的字段，字段类型必须正确；空响应、多个对象、多动作、缺失字段、未知字段和阶段不匹配均属于格式或规则错误。
- 模型的 `reason` 只作为角色说明。程序不因其中的金额、命令或“已经成交”等文字执行额外动作；可验证的分析结论始终使用本地数据。台词不得声称知道隐藏箱值；如出现矛盾，不能把这段台词作为事实分析呈现。

实际模型输入必须可检查，以验证未泄露箱号金额映射、种子、配置秘密和选手箱值。模型调用不得直接接收整个 SQLite 检查点或内部状态对象。

#### 13. 终端展示与记录

每次等待人类操作时，至少展示：局 ID、当前阶段、轮次与开箱配额；20 个箱子的状态；自己的保留箱；仍在场的奖金和已排除金额；当前有效报价及可选操作；已使用的提前来电次数。初选前保留箱标为“尚未选择”，无有效报价时明确标为“暂无报价”，不沿用上一次失效金额。

箱子必须清楚区分“自己的未开箱”“其他未开箱”“已开箱及金额”。展示不得把自己的箱子误写成金额已知，也不得把打开其他箱子时排除的金额累计成选手收入。

每次开箱、正常来电、提前来电、拒绝、还价、还价被拒、成交和最终揭晓都单独形成可读事件。提前来电应明确显示“银行家提前来电”，并说明原本本轮还需开几个箱子；恢复开箱时继续显示该配额。

界面只在需要用户决定时等待输入，不要求在每一句台词后按回车。模型响应等待、纠错重试和网络重试显示状态；错误信息不能混同为已生效事件。颜色只能辅助阅读，纯文本输出也应能辨认状态。命令菜单和数据分析即可满足首版，不以复杂终端排版为完成条件。

每局保存三类本地记录：

- **有效事件记录**：事件 ID、状态版本、轮次、行动方、合法动作、实际金额、配额变化与结果；数值足以重建公开过程及报价分析。
- **调用与错误记录**：模型名称、脱敏接口地址、实际发送的 messages、原始可见响应、解析结果、重试原因、耗时，以及接口实际提供的 token 用量。隐藏推理字段不作为游戏记录或教学分析保存，未提供的用量不得猜测。
- **私有存档**：支持恢复的完整权威状态，包含隐藏箱子映射；与面向用户的公开记录和提示词明确区分。

API 密钥和 Authorization 等凭据不得写入提示词、日志或源码。记录路径按局区分，运行存档、实际密钥和调用日志不纳入源码交付。检查点或必要事件记录写入失败时停止推进并报告，不能显示“保存成功”后继续请求下一动作。

#### 14. 错误处理、重试与主动退出

人类输入错误只在当前菜单反馈，不请求模型、不消耗机会、不改变状态。无效箱号、重复开箱、试图打开自己的箱子、过期报价操作、重复还价和非整数金额都必须有明确提示。

模型格式错误、阶段不匹配或非法动作，由同一银行家在同一局面纠正。默认一个决策最多允许三次完整生成，即首次加两次纠正；耗尽后保存当前局面并报告本次决策未完成，不自动替银行家选择 `wait`、报价或接受还价。

请求超时、限流和暂时性服务失败属于 API 错误，不属于游戏违规。默认单次请求超时为 120 秒，暂时性错误最多额外重试两次，等待间隔为 1 秒、2 秒；参数应可配置。网络重试与动作纠正分别计数，不能相互重置形成无限重试。失败响应不消耗来电或还价资格。

认证失败、模型不存在、配置缺失、上下文超限、连续空响应或生成截断等情况需要明确报告；空响应与截断只允许在上述有限决策尝试内重试，不执行看似完整的半段动作。达到限制后保留最后有效检查点并停止本次运行，不宣布选手或银行家失败。首版不静默截断历史以绕过上下文上限。

用户选择保存退出，或通过 `Ctrl+C` 中止时，报告“本局未完成”，说明最后已确认保存的位置。若中止发生在请求过程中，不承诺该外部请求不会产生用量；未验证、未提交的响应不得当作有效动作。重新运行可以从最后一致的检查点继续。

未预期程序异常、状态不一致或存档损坏属于程序错误，不能伪装成模型违规反复重试。已经成交或最终开箱结算后，任何迟到输入、迟到响应和重复恢复都不得重新结算。

#### 15. 结算与复盘

正常完成只有以下三种情况：

1. 选手接受当前报价，所得为该报价。
2. 选手提出合法还价且银行家接受，所得为该还价。
3. 选手拒绝第六轮的最终报价，所得为自己最初保留箱子的真实金额。

结果确定后立即终止游戏决策，揭晓选手箱值和其余尚未公开的箱子，展示本局完整分配。结果揭晓不追加成新的可操作开箱回合，不引起新报价，也不改变成交金额。

复盘至少展示：最终所得、结束方式、自己的箱值、六轮内实际发生的开箱顺序、每次有效报价时的剩余金额与期望值、报价比例、正常或提前来电、选手的接受/拒绝/还价，以及银行家当时提交的简短理由。复盘的数值由保存事件生成，首版不额外调用模型撰写长报告。

成交价与最终箱值的差额可以展示，但必须标明是“事后结果对比”，不等于当时策略的质量。复盘评价当时的局面时，只使用当时已经公开的信息，不能以已经揭晓的大奖倒推“你当时一定应该继续”。

若中途成交，可以确定“如果拒绝全部报价并始终持有原箱，最后会得到多少”；不能确定“如果这次拒绝，下一通电话会报价多少”。首版不生成未实际发生的后续报价，也不把重新运行模型产生的另一条路径当作必然历史。

#### 16. 完成与验收标准

后续实现交付应包含适用 Python 版本、依赖说明、新局与恢复的启动方式、模型配置说明、不含真实密钥的配置示例，以及上述默认规则。本次文档起草不包含这些实现工作，也不更新现有依赖或环境。

实现完成后，应使用固定分配或模拟响应验证至少以下行为：

- 20 个箱子和 20 档奖金一一对应；分配先于选手选择；开箱、重试、暂停和恢复都不改变未开箱金额。
- 选手箱子不能在游戏中被打开；重复箱号、错误阶段及非法金额均被拒绝且状态不变。
- 正常开箱配额严格为 `5、4、3、3、2、1`，最终报价前恰好累计打开 18 个箱子，剩余两个中包含选手箱子。
- 正常报价不能选择 `wait`；合资格的提前来电可以选择 `wait`；每局最多两次、每轮最多一次提前报价，重试不消耗额度。
- 提前报价被拒绝后继续原轮剩余配额，轮末仍会正常报价；同时满足轮末与来电条件时只产生正常报价。
- 初始报价采用当前轮三个档位之一，计算、取整、最低金额保护与展示一致；模型自报金额不能覆盖程序金额。
- 每个有效报价最多一次合法还价；银行家接受就按还价立即成交，拒绝则保留原价，不能生成第三个金额或再次还价。
- 接受报价、还价成交和最终拒绝三种路径都能正确结算，且终局后不再请求任何游戏决策。
- 概率计算包含选手箱子，正确处理低于、等于、高于报价三种情况；第 9 节示例数值正确。
- 玩家页面、模型实际请求、纠错文本和终局前分析都没有隐藏箱值、完整映射、随机种子或接口秘密。
- `explain()` 不请求模型、不推进轮次、不改变报价或次数；策略推测与可验证统计有清楚区分。
- 在等待开箱、提前报价答复和还价后的最终选择等位置保存退出，再恢复时，箱子、配额、有效报价、来电额度及还价资格保持一致。
- 重复恢复输入、非法响应和网络重试不重复开箱、扣次数、成交或追加有效事件；游戏事件与调用尝试能分别追踪。
- 接口失败、纠正耗尽、存档失败和用户中止都得到明确的未完成状态，不能变成一方获胜或默认成交。
- 最终揭晓只改变信息可见性，不改变既定奖金；复盘能区分当时可知信息、事后箱值与未发生的反事实。
- 在配置有效、接口可用且银行家给出合法响应的条件下，人类能仅通过菜单从开局玩到完整结算，无须修改代码或手动修补状态。

以上验收以首版“人类选手＋AI 银行家”的可运行单局为限。银行家模式、AI 对局观战和图形界面留待人类审核后另行定义，不因本文件描述了完整设想而自动纳入本次实现。

### LangGraph 设计结构（AI）

本节把前面的规则落实为状态、节点和边的设计草案，仍未开始实现游戏。配套图为 [LangGraph 设计结构图（横向 A4，单页）](output/pdf/langgraph-design.pdf)，版本 `DESIGN 01`；图与以下节点名称一一对应。图中的 `P`、`S` 是避免交叉线的同名连接标记，分别指向 `await_player`、`settle`，不是额外节点。

#### 17. 设计总览：一个状态，九个节点

使用一个 `StateGraph(GameState)`，按顺序执行节点，不引入并行分支、子图或多 Agent 调度。银行家在“正常报价”“提前来电判断”“还价答复”三种上下文中复用同一个调用节点；人类在初选、开箱和报价决定三个阶段复用同一个暂停节点。

可以将三个概念理解为：状态保存“这一局现在是什么样”；节点完成“一次输入、一次请求或一次规则处理”；边根据已经得到的结果决定“下一步去哪里”。节点返回状态更新，条件边只读状态，不调用模型、不改变规则数据。该用法对应 [LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api) 的状态、节点及条件边机制。

| 类型 | 节点 |
| --- | --- |
| 本地初始化 | `init_game` |
| 人类输入与本地执行 | `await_player`、`apply_player` |
| AI 请求、校验与本地执行 | `bank_decide`、`validate_bank`、`apply_bank` |
| 完成结算与复盘 | `settle`、`review` |
| 可恢复的调用故障 | `await_recovery` |

`START`、`END` 是 LangGraph 的入口和终止标记，不计入九个业务节点。只有 `bank_decide` 调用模型；`await_player` 和 `await_recovery` 使用 `interrupt()`；其他节点都是本地确定性逻辑。

#### 18. State：字段、更新方式与可见范围

`GameState` 建议用 `TypedDict` 定义，内部记录使用可序列化的字典和列表。类型定义约束开发时的结构；实际动作、字段类型与状态不变量仍须由运行时校验，不能把 `TypedDict` 当作自动裁判。

| 字段 | 建议类型与初值 | 含义及允许的写入方 |
| --- | --- | --- |
| `game_id`、`rule_version`、`rules` | `str`、`str`、规则快照 | `init_game` 写入后不变；快照含奖金表、轮次配额、系数和来电上限 |
| `box_values` | `dict[int, int]` | 私有箱号金额映射，只由 `init_game` 生成；后续不可修改 |
| `own_box` | `int 或 None`，初始 `None` | `apply_player` 在初选合法后写入，之后不变 |
| `opened` | `list[OpenedBox]`，初始空列表 | 已开箱的顺序记录；每项包含箱号、金额和事件 ID，由 `apply_player` 追加 |
| `round_no`、`opened_in_round` | `int`，初始 `1`、`0` | 轮次与本轮已开数；仅 `apply_player` 在合法开箱或拒绝正常报价进入下一轮时更新 |
| `early_used`、`early_used_this_round` | `int`、`bool`，初始 `0`、`False` | `apply_bank` 发布提前报价时更新；只有进入下一轮才由 `apply_player` 重置轮内标记 |
| `phase` | 阶段枚举，初始 `CHOOSE` | 见下表；只有本地状态节点改变业务阶段 |
| `current_offer` | `Offer 或 None`，初始 `None` | 当前有效报价，由 `apply_bank` 发布；`apply_player` 拒绝时清空，`settle` 完成结算后清空 |
| `counter_amount` | `int 或 None`，初始 `None` | `apply_player` 提交合法还价时写入；答复处理后清空；`Offer.counter_used` 保留使用痕迹 |
| `pending_player` | `ActionEnvelope 或 None` | `await_player` 收到的恢复值，只是待验证输入；`apply_player` 使用后清空 |
| `bank_task` | `NORMAL / EARLY / COUNTER 或 None` | `apply_player` 根据当前动作与资格设定，`apply_bank` 完成决策后清空 |
| `bank_draft`、`bank_action` | `Candidate 或 None`、`ValidatedAction 或 None` | `bank_decide` 写候选及校验元数据；`validate_bank` 写合法动作；`apply_bank` 消费并清空 |
| `generation_attempt`、`feedback` | `int`、`Feedback 或 None` | 生成次数与最近输入/调用错误；反馈标注来源和错误码，成功处理后清除，不是游戏事件 |
| `history`、`version` | `list[Event]`、`int`，初始空列表、`0` | 本地状态节点提交有效事件时同时更新；失败、看分析和保存退出不推进版本 |
| `settlement` | `SettlementIntent 或 None` | `apply_player` 或 `apply_bank` 设置待结算原因及成交金额；箱值结算由 `settle` 读取真值 |
| `result`、`review_data` | 结果字典、复盘字典，初始 `None` | 分别仅由 `settle`、`review` 写入 |

几个复合记录的边界如下：

- `Offer` 至少包含 `offer_id`、`kind`（`NORMAL / EARLY`）、轮次、实际金额、档位、系数、报价时的统计依据、简短理由与 `counter_used`。这些内容在报价发布时固定，不能随之后的状态重新计算而覆盖历史。
- `ActionEnvelope` 包含 `request_id`、`expected_version` 和具体动作。暂停问题的请求标识由局 ID、状态版本及阶段稳定生成；恢复时检验其与当前问题是否对应。用户输入错误可以继续使用同一个未完成请求，不生成假事件。
- `Candidate` 包含可见文本、生成结束原因、本次 `bank_task` 和请求绑定的状态版本；截断响应即使看似完整也不执行。`ValidatedAction` 保留经过校验的动作和绑定版本，执行前再次确认其未过期；模型不能自行指定或覆盖该版本。
- `Event` 包含唯一事件 ID、递增版本、行动者、动作和已提交结果；报价还需保存当时的公开局面快照。可以用局 ID 加新版本构成事件 ID，已有相同 ID 的记录不能再次追加。
- `SettlementIntent` 的原因仅为 `DEAL / COUNTER_DEAL / OWN_BOX`；`result` 保存最终金额、原因、原始箱值与最终揭晓。模型不得直接填写 `result`。
- API 客户端、密钥、数据库连接与文件句柄放在图外运行上下文，不放入可持久化的 `GameState`；检查点也不是配置密钥的存储位置。

业务阶段与图节点位置分开表达：

| `phase` | 当前允许发生的业务 |
| --- | --- |
| `CHOOSE` | 等待选手确定自己的箱子 |
| `OPEN` | 等待开箱，或处理本次开箱之后的银行家介入判断 |
| `OFFER` | 有有效报价，等待选手接受、拒绝或还价 |
| `COUNTER` | 合法还价已提交，等待银行家答复；原报价仍保存但暂不接受新的玩家动作 |
| `SETTLE` | 原因已经确定，等待本地结算 |
| `DONE` | 结果已经确定，只生成或查看复盘 |

`phase` 不负责记录“模型请求到一半”等运行位置，这部分由 LangGraph 检查点的待执行节点和中断信息承担。调用失败不把 `phase` 改成结束状态。

所有字段先使用默认的覆盖更新方式，不使用 `MessagesState`，也不为 `history` 配置无条件的 `operator.add` 追加。节点以新列表返回 `history = [*旧历史, 新事件]`，并返回相关字段的同一份更新；不原地修改传入的字典或列表。首版是串行图，无须引入并行合并的 reducer；未来若并行才重新设计冲突和去重语义。

未开箱集合、剩余金额、剩余配额、统计量和候选报价是**派生视图**，按本次状态即时计算，不维护另一套可独立修改的值。`public_view(state)` 专门生成玩家界面和银行家提示词允许使用的字段；禁止输出完整状态。即使字段名带 `private`，检查点、调试流或 `stream_mode="values"` 也不会自动替应用保密，终端与 API 必须使用白名单投影。

每次有效提交后检查：原始映射仍有 20 个不同箱号；开箱记录无重复且不含自己的箱子；轮内开箱数在配额内；未开箱数等于 `20 - len(opened)`；提前次数不超限；`OFFER / COUNTER` 必须有有效报价；`DONE` 必须有结果。

#### 19. Nodes：每个节点只负责一个边界

| 节点 | 读取与执行 | 返回的更新及后续 |
| --- | --- | --- |
| `init_game` | 只在新局创建规则快照、均匀随机映射和初始字段 | 完整初始状态；进入 `await_player`。恢复不经过此节点；意外拿已有局再次初始化应拒绝 |
| `await_player` | 根据 `phase` 生成公开菜单和稳定的请求标识，调用一次 `interrupt(payload)` | 人类恢复后仅返回 `pending_player`，不校验成交、不打开箱子、不请求 AI |
| `apply_player` | 校验请求版本、阶段和动作；执行合法初选、开箱、拒绝、还价或成交意向 | 一次返回权威状态更新、有效事件及下一阶段；错误仅写反馈并回到 `await_player` |
| `bank_decide` | 按 `bank_task` 构造公开提示词，发起一次完整生成；内部执行有限 HTTP 重试 | 候选文本与生成计数，交给 `validate_bank`；调用失败耗尽则写错误并转 `await_recovery` |
| `validate_bank` | 解析 JSON，检查字段、阶段、可选动作、档位、理由长度及候选绑定版本 | 合法则写 `bank_action`；可纠正则写反馈并返回 `bank_decide`；生成次数耗尽则转 `await_recovery` |
| `apply_bank` | 只接收已验证动作；计算并发布报价，或提交 `wait`、保留原价、接受还价 | 更新报价、提前额度、阶段及有效历史；清空本次银行家临时字段；回到玩家或进入结算 |
| `settle` | 按 `settlement` 取成交金额，或读取自己的真实箱值；检查尚未结算 | 一次写入 `result`、最终事件和 `phase=DONE`，关闭报价，然后进入 `review` |
| `review` | 从已提交事件与结果生成数值复盘、揭晓信息及稳定的结果视图，不调用模型 | 写 `review_data` 后到 `END`；重复生成应得到相同复盘数据 |
| `await_recovery` | 展示脱敏故障，使用独立的 `interrupt()` 等待“显式重试”；也允许界面保存退出 | 重试仅清理本决策的错误与计数，保留 `bank_task` 和全部游戏事实，回到 `bank_decide` |

每次建立一个新的 `bank_task` 时，将 `generation_attempt` 设为 0 并清空旧候选；每次完整生成尝试加 1。格式纠正沿用同一任务和局面，最多三次生成；一个完整生成中的 HTTP 重试不额外消耗游戏机会。用户在故障菜单明确选择重试，才开启新的有限尝试周期，程序不能自行无限重置计数。

合法还价在 `apply_player` 中就将 `current_offer.counter_used=True`、`counter_amount` 写入并设 `phase=COUNTER`。之后即使银行家接口失败，这次已提交还价也继续存在，不能恢复成“可以再还价”；失败的模型响应只是不再额外消耗机会。`keep_offer` 清空待处理还价、恢复 `OFFER`，保留已用还价标记；`accept_counter` 保存成交意向后进入 `SETTLE`。

#### 20. Edges：固定连线和条件分支

固定边只用于下一步唯一的情况；有多种结果的源节点只注册条件边，不能再额外挂一条无条件边，否则可能同时执行多个后继。

| 起点 | 条件或事件 | 终点 |
| --- | --- | --- |
| `START` | 新局启动 | `init_game` |
| `init_game` | 初始化完成 | `await_player` |
| `await_player` | 收到恢复值 | `apply_player` |
| `apply_player` | 初选完成、输入错误、无需银行家介入的开箱、拒绝报价后继续开箱 | `await_player` |
| `apply_player` | 轮末正常报价、符合提前来电条件，或合法还价 | `bank_decide` |
| `apply_player` | `deal()`，或最终轮 `no_deal()` | `settle` |
| `bank_decide` | 得到可见候选文本，含需进一步判定的空白或截断结果 | `validate_bank` |
| `bank_decide` | 不可恢复配置错误或有限网络尝试耗尽 | `await_recovery` |
| `validate_bank` | 合法动作 | `apply_bank` |
| `validate_bank` | 非法候选且 `generation_attempt < 3` | `bank_decide` |
| `validate_bank` | 非法候选且已用完生成次数 | `await_recovery` |
| `apply_bank` | 正常/提前 `offer`、提前判断 `wait`、还价答复 `keep_offer` | `await_player` |
| `apply_bank` | 还价答复 `accept_counter` | `settle` |
| `settle` | 结果已经提交 | `review` |
| `review` | 复盘完成 | `END` |
| `await_recovery` | 用户明确要求重试同一银行家决策 | `bank_decide` |

`apply_player` 之后的路由遵循以下优先级；所有字段由该节点完成校验和提交后再读取：

1. 当前输入非法，回到 `await_player`，不执行其他分支。
2. 已形成结算意向，进入 `settle`。
3. 合法还价已提交，设置 `bank_task=COUNTER` 并进入 `bank_decide`。
4. 刚合法打开一个箱子：本轮配额已满时设置 `NORMAL`；否则仅在 `early_used < 2` 且本轮未提前来电时设置 `EARLY`；两者均不满足就继续等待开箱。
5. 其他合法动作回到 `await_player`。拒绝提前报价后不能针对同一个开箱事件再次触发来电；必须等下一个合法开箱才重新检查。

拒绝正常报价且轮次小于 6 时，`apply_player` 将 `round_no` 加 1、`opened_in_round` 清零、轮内提前标记清零，清空报价并回到 `OPEN`；拒绝提前报价仅清空报价并回到 `OPEN`，不改配额；第六轮拒绝设置 `settlement=OWN_BOX`。

银行家 `wait` 只结束这一次决策并回到 `OPEN`，不能立即再次走回 `bank_decide`。银行家发布报价则进入 `OFFER`；轮次未结束的提前报价只能在 `apply_bank` 真正发布时增加来电次数。

路由函数可以命名为 `route_player`、`route_bank_call`、`route_validation`、`route_bank_commit`，分别挂在四个有分支的节点后。函数返回上表中的目标名称，每次选择一个后继；路由函数本身不是图节点，也不重复校验或应用动作。

#### 21. 暂停、恢复与图外界面

`await_player` 的中断值只包含公开问题、可选动作和请求标识；通过同一 `thread_id` 的 `Command(resume=输入封装)` 继续。中断恢复会重新执行所在节点，因此中断前只生成确定性的展示数据；不能在那里随机洗箱、请求模型、写交易或增加计数。框架的中断不能被通用异常处理吞掉。[LangGraph 中断文档](https://docs.langchain.com/oss/python/langgraph/interrupts)

菜单中的 `explain()` 和 `save_exit()` 由终端控制器在图已经暂停时直接处理。前者读取当前检查点的公开投影并展示统计，后者保留当前暂停点并退出进程；两者都不发送 `Command(resume=...)`，所以不会消费当前问题、推进版本或形成“从 END 恢复”的伪流程。这是第 8 节用户操作到图执行的映射，不新增游戏动作。

`await_recovery` 是专门等待用户处理调用故障的操作节点，不能接受 `deal`、开箱或还价。用户可以修正图外 API 配置后重试原任务，也可以保存退出；原有报价和待处理还价始终保留。状态损坏、数据库写入失败等程序问题停止在最后一致检查点，不伪装成可重试的银行家决策错误。

新局用新的 `thread_id` 和初始化输入启动；已经在 `interrupt()` 处暂停的局使用同一 ID 加恢复值；进程在普通节点间中止、已有可继续任务而没有待答中断时，用同一 ID 从检查点继续，不再次传入新局数据。是否有中断或待执行节点由保存的检查点决定，不能只看 `phase` 推测。[LangGraph 持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)

同一局只允许一个本地执行者，不支持两个进程同时恢复。状态版本和请求标识用于拒绝旧输入；节点返回更新后由检查点提交，不在提交前向用户宣布动作已生效。对外事件导出按事件 ID 幂等写入，避免崩溃重跑重复日志；外部模型仍可能被再次请求，不能据此声称整个系统实现了外部调用的“恰好一次”。

`review → END` 是正常完成的唯一出口；保存退出留在原中断点，银行家故障留在恢复中断点，二者均没有正常终局边。图的执行步数上限只作为发现意外循环的保护，达到时报告未完成，不把它当作第七轮、默认成交或胜负条件。

#### 22. 用三条路径核对设计

- **一次提前来电**：`await_player → apply_player（开箱）→ bank_decide（EARLY）→ validate_bank → apply_bank（offer）→ await_player`。玩家拒绝后，经 `apply_player` 回到开箱等待，本轮剩余配额保持不变。
- **还价被接受**：`await_player → apply_player（counter）→ bank_decide（COUNTER）→ validate_bank → apply_bank（accept_counter）→ settle → review → END`。成交金额来自已经校验的还价，银行家没有再生成金额的权限。
- **正常报价连续格式错误**：`bank_decide → validate_bank → bank_decide` 有限纠正，耗尽后到 `await_recovery`。本轮已开的箱子不会重开，尚未发布的报价不会显示为生效，只有用户明确重试才返回请求节点。

后续实现时，应将第 16 节的业务验收与这些图路径一起验证；本次交付只增加设计说明和配套 PDF，不新增游戏代码或更改依赖。
